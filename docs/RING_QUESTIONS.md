## Still open

1. **Partner Token Exchange inbound contract:** The M5 Configure/deployment pages fetched on 2026-10-17 said Ring POSTs an authorization code to the partner Token Exchange URL and the code must be exchanged within 60 seconds. That review did not find the exact incoming Content-Type, body field/nesting, required headers/authentication, or success response Ring expects. Could you provide a sanitized canonical request and response example, including timeout and retry behavior? Is a JSON or `application/x-www-form-urlencoded` body with a top-level `code` field supported, or is another shape required?

2. **Canonical webhook event inventory:** The Ring API reference fetched during M5 listed doorbell, motion, device lifecycle, app integration, subscription, and sensor events; the Ring API Development Guide's Build section summarized only motion/device-add/device-remove events. Which event inventory is current for partner webhook delivery, and are the listed sensor event types enabled for ordinary partner apps? The API reference's sensor example also used an opaque, non-UUID-shaped `meta.request_id`; please confirm the required ID constraints for all v1.1 event types. M7 could not re-check either page.

3. **Sandbox/staging requirements:** Getting Started describes a synthetic sandbox with test devices/events, while the Develop testing guide describes staging users with an active Ring Protection plan and currently US-located devices. Which Ring sandbox is available to developers, how is it enabled in the portal, and does it require a real Ring account/device or subscription? No paid resource or portal app was created for this verification.

## Findings from the M5 public-documentation review (not reverified in M7)

- **Motion subtype field:** The M5 API reference/Motion Detection pages put the canonical subtype at `data.attributes.sub_type`; the earlier supplied example used `data.subType`. Doorway Relay treats that only as a compatibility fallback. M7 did not re-fetch the pages.
- **One-way account-link redirect:** Pages checked during M5 showed the Account Link URL receiving `time` and `nonce` query parameters; the partner obtains Account ID from an unclaimed token's `/v1/users/me` profile and matches the HMAC nonce. The App Integrations sequence was POST nonce verification, then PATCH status `completed`. Doorway Relay implements this sequence and tests it with stubs; it is not Ring-tested. M7 did not re-fetch these pages. Still open: Ring's inbound Token Exchange callback remains unverified in this project, so the route cannot obtain a live unclaimed token through that integration until Ring confirms the contract.
- **Source availability:** The old standalone `notifications.html`, `motion-detection.html`, `button-press.html`, and `account-linking.html` links returned 404 in the 2026-10-17 M5 follow-up. M5 then fetched the consolidated [`Ring Partner API Documentation`](https://developer.amazon.com/docs/ring/api-documentation.html) and Getting Started/Configure/Develop pages. These are historical M5 observations; M7 could not verify their current availability/content.
