# Security and privacy review (M11 source review; historical M6–M10 notes retained)

**Review date:** 2026-10-20

**Scope:** Source/configuration review plus local automated checks. This is not a penetration test, formal audit, Ring certification, or production approval.

## Implemented controls verified in source

- **Authentication:** passwords use Node `scrypt` with a per-user random salt. Session IDs are random, HMAC-signed, and stored in SQLite only as SHA-256 hashes. The HTTP-only, `SameSite=Lax` cookie is marked `Secure` in production. Login rotates the session; sessions expire after seven days. First-user registration rechecks and inserts inside an immediate SQLite transaction so only one initial account can be created. Authentication and public webhook routes are rate-limited.
- **CSRF / origin:** browser mutations require a session-bound CSRF token and the exact configured `WEB_ORIGIN`; cross-site Fetch Metadata is rejected. `WEB_ORIGIN` is validated as an HTTP(S) origin with no credentials, path, query, or fragment. It must be HTTPS in production.
- **Authorization:** protected API reads and mutations require an enabled signed-in user. The workspace is intentionally single-tenant: every enabled user shares the same workspace records. There is no per-household/organization authorization boundary or role model.
- **Browser boundary:** the UI uses same-origin relative `/api/...` requests with `credentials: "same-origin"`; the CSRF token is held in module memory rather than persistent browser storage. Source search found no `dangerouslySetInnerHTML`/`innerHTML` sinks, `localStorage`, or `sessionStorage` usage; React renders user text as text.
- **Validation / errors:** request bodies and query strings are Zod-validated, most write schemas reject unknown fields, and body/rate limits are configured. SQL uses prepared statements. Multi-row lifecycle and webhook writes use SQLite transactions. Unexpected API errors return a generic response without a stack; Ring upstream failures do not return credential-bearing details.
- **Ring signature and deduplication:** the webhook verifies HMAC-SHA256 over the exact raw body with a constant-time comparison before parsing JSON. Simulator and Ring signing keys are distinct, and simulator provenance remains `ring_simulated`. Request-ID and event-ID deduplication are protected by database uniqueness/transactions. The endpoint is rate-limited and capped at 256 KiB.
- **Ring provenance configuration:** if a Ring client ID/secret, HMAC key, API token, or history device is configured, `RING_EVENT_SOURCE` must be explicitly set to `ring_live` or `ring_playground`. The simulator key always maps to `ring_simulated`; Ring-HMAC webhooks are accepted only under `ring_live`, while `ring_playground` is reserved for authenticated Playground API access and rejects Ring-HMAC webhook traffic. A Playground bearer token's source remains an operator configuration, not a property inferred from token contents.
- **Privacy minimization:** raw webhook bodies are not retained; receipts retain a request ID, payload digest, provenance, and receive time. Supported events store limited event/device metadata and a controlled neutral summary. The optional Playground WHEP path can receive/display a browser video stream after an explicit user action, but does not record, capture frames, download snapshots, or persist media. No audio transceiver is requested. Avoid entering names or sensitive details in handoff notes.
- **Tokens and logs:** persisted Ring OAuth access/refresh tokens are AES-256-GCM encrypted with a server-side 32-byte key. The separate Playground token is env-only and never persisted. Playground status/verify responses return only bounded safe device IDs/types plus summary/state/selection; they do not return the token, raw API body, upstream `Location`, or arbitrary URLs. IDs remain opaque and are held in process memory for selection. The `ring:probe` reporter emits bounded structure, allow-listed event names, and subtype/classification paths/types without their values; unknown/dynamic keys are redacted and a final token/email/URL rejection check runs before output. The report writer requests mode `0600` where the OS honors it. Credentials are not returned to browser code. The optional Token Exchange rejection log is generic and omits submitted field names and values. The local simulator key is rejected in production.
- **WHEP relay:** authenticated + CSRF + same/trusted-origin controls and a 10-per-minute rate limit protect create/delete routes. SDP is capped at 64 KiB and structurally restricted to one receive-only video m-line; Ring API origin, HTTPS, redirect behavior, bounded answer SDP, and session `Location` are validated. Requests time out after 10 seconds. At most one in-memory session per app process lives for five minutes; stop, expiry, identity/device change, and shutdown attempt DELETE, and shutdown aborts/awaits an in-flight create. Responses are `no-store`; the browser receives an app session ID/answer, not the token or Ring `Location`. Cleanup is best-effort when the upstream is unavailable; this process-local design is not a multi-instance production session store. These controls have mocked/fake-peer tests only; no real Ring session was exercised.
- **WHEP ICE privacy:** the browser creates `RTCPeerConnection` without configured STUN/TURN servers, but ICE gathering may still add host candidates or mDNS/network identifiers. The full offer SDP is sent to this app server and relayed to Ring. No candidate/IP filtering is implemented; do not use the feature where disclosure of local network metadata is unacceptable. Real browser candidate behavior and Ring handling remain unverified. The video uses `object-fit: contain` with no CSS crop, filter, transform, or overlay while live; actual watermark visibility still needs human review.
- **Runtime safety:** the API and Vite development server bind to loopback by default. Production configuration requires an HTTPS web origin, the documented HTTPS Ring API/OAuth origins, a same-origin HTTPS token URL, a 64-hex-character session secret, and an absolute SQLite path; non-HTTPS Ring URLs are rejected in all environments. The Ring API client rejects cross-origin request paths and redirects; OAuth token/profile requests also reject redirects. The API client applies a 12-second per-request timeout and a 2 MB streamed JSON response cap, and bounds retries. OAuth refresh has a 12-second deadline; authorization-code exchange/profile remains bounded at 55 seconds. These controls are covered by local mocked tests, not live Ring measurements. Production config also rejects the simulator signing key and enabling the unverified inbound Token Exchange route. Demo seeding is blocked when `NODE_ENV=production`. The public `/api/health` endpoint executes only `SELECT 1`, returns a generic 503 if SQLite is unavailable, and creates no session.

See [`ARCHITECTURE.md`](ARCHITECTURE.md), [`API.md`](API.md), and [`RING_INTEGRATION.md`](RING_INTEGRATION.md) for route and data-flow details.

## Remaining risks and limits

- This is a demo-grade, single-workspace application. There is no multi-tenant isolation, user administration, email verification, password reset, MFA, formal session revocation workflow, configured retention policy, or audited backup/restore process.
- SQLite is plaintext except for encrypted Ring token columns. The file, WAL/SHM sidecars, backups, logs, and host must be access-controlled. Loss of the token-encryption key makes stored Ring tokens unusable; a leaked key compromises those encrypted tokens.
- `.env` is a local-file convention, not a production secret manager. Use an approved secret store and narrowly scoped runtime access before any deployment. Never send credentials, private device identifiers, or personal data through chat, screenshots, logs, or documentation.
- The deployment path has no production server build/start script, container/service definition, or backup/restore validation. The health endpoint checks SQLite only. Operational monitoring, alerting, rate-limit tuning, proxy configuration, and recovery behavior remain unverified.
- The inbound Ring Token Exchange request/acknowledgement contract remains unverified. `RING_TOKEN_EXCHANGE_ROUTE_ENABLED` must remain `false`; the route returns 503 before parsing while disabled. The legacy Event History parser retains historical response-field/timestamp assumptions, is opt-in for `ring_live`, and has not been checked against a real response; it cannot be used for Playground ingestion. The owner says a Playground probe was run on their machine, but no redacted report or findings were supplied here, so this workspace has no reviewed response schema. The local simulator is synthetic and does not establish live Ring connectivity.

## M6–M10 scan/check coverage

- `npm audit` is a dependency advisory check, not a secret scanner.
- Dedicated secret/static-analysis utilities (`gitleaks`, `trufflehog`, `detect-secrets`, `semgrep`, `osv-scanner`, `grype`, `syft`, and `bandit`) were not installed in this environment. No result from those tools is claimed.
- A local heuristic scan was run across readable, non-generated workspace files for selected high-confidence token/private-key patterns. Its outcome and coverage are recorded in [`TESTING.md`](TESTING.md). A clean heuristic result is **not** proof that the repository is secret-free.
- `.env`, `.env.local`, and `.env.production` were absent at M6 inspection. In M7, the root env-file inventory again contained only `.env.example`; this is a presence check, not a repository-wide guarantee.
- At M6 start, Git reported only `README.md` as tracked/modified and the application/docs as untracked. At M7 recovery, the reachable local history was still only the shallow initial commit; 111 unreachable blobs matched the then-current workspace, but no unreachable commits or trees existed. Therefore scans do not verify missing historical commits or remote history. No reset, rebase, or history rewrite was performed; M7 changes are documented in `TESTING.md` and `BUILD_LOG.md`.

## Safe defaults

Keep `RING_TOKEN_EXCHANGE_ROUTE_ENABLED=false` and `RING_HISTORY_POLLING_ENABLED=false`; the legacy poller cannot run for `ring_playground`. Keep Playground tokens server-side in the ignored `.env`; use a generated session secret and token-encryption key; do not expose the loopback development server. The current Playground history Sync route is fail-closed until a real redacted probe report is reviewed. Any public HTTPS endpoint, tunnel, deployment, or live Ring test requires separate explicit authorization and a reviewed endpoint/security plan.
